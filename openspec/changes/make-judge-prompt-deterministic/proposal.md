# 判分提示词必须可复现：修掉 model_based 的集合迭代序

> 日期：2026-09-22 ｜ 无对应研究文档条目（提案由代码审计发现，非路线图项）
> 修订（同日）：并入 `verdict_drift` 的归因盲区修复 —— 它由本变更自己的验收记录暴露，且是本变更归因论证的实际依赖。

## Why

`model_based` 评分器把工具清单以 `list(set(...))` 拼进 judge 提示词（`graders/model_based.py:158`）。Python 对字符串的 hash 默认按进程随机化，因此**同一批归档字节在不同进程里 regrade 会生成不同的提示词**。

变更④ 把「采集与评分分离」立为契约，承诺"改判据、换 judge、收紧证据声明，都能对同一批字节重评"——而这条承诺成立的前提是：重评时喂给 judge 的东西与上次逐字节相同。今天它不成立。

这不是理论风险。一个用了两种以上工具、且判据读到工具清单的套件，其分数在跨进程重评时可能漂移；而 `verdict_drift` 会把这种漂移读成"judge 升级翻转了 N 个 trial"——**把不可复现误报成口径变化的收益**，正好污染④ 用来审计口径的那个工具。

它同时是后续一切判分器信度测量的前置：在提示词本身不可复现的前提下测"这条判据稳不稳"，测出来的全是噪声。

**第二个 Why（并入项）**：做上面这件事时撞见了 `verdict_drift` 自身的缺陷。它的跨 attempt 口径聚合元组只有四根轴（属性翻译表版本、规范修订、统计口径版本、判定模型），**不含判分实现版本**——于是本变更 v2→v3 这次重评报出 `distinct_calibers = 1`，字面意思是"两次 attempt 口径相同"，而实际有一根轴变了。误报方向是最危险的那一侧：`>1` 让人怀疑归因，`=1` 让人**以为已经排他**。验收记录只能靠人工逐 attempt 比对兜住，并把这件事写成了注意事项。

而 `orchestration` 早已承诺得更清楚：现有 Requirement 明确把「判分实现版本」列为必须记录的口径，其场景要求"可查看全部判定条目及各自口径标识，**指出是哪一项版本变了**"。记录侧做到了（`GradeAttempt.grader_versions` 已落盘），**聚合归因侧没做到**——一个计数回答不了"哪一项"。

## What Changes

1. **提示词成为纯函数**：`_build_prompt` 中所有由集合派生的列举改为确定序，使提示词输出完全由（归档证据, rubric, dimensions, 判分配置）决定。
2. **`ModelBasedGrader.implementation_version` `"2"` → `"3"`**。这是行为变更：修复后重评历史 run 可能翻转动到多个 verdict。**不静默处理**——翻转数量由 `verdict_drift` 量出并记入本变更的验证记录，延续"历史 verdict 永不覆盖、口径随判定落盘"的既有纪律。
3. **守护测试覆盖一类而非一点**：同一份归档证据在**两个独立子进程**中各构建一次判分输入，断言逐字节相等。测试约束的是"集合序泄进判分输入"这一整类缺陷，而不只是今天已知的这一处。
4. **审计结论落档**（见 design.md）：`graders/`、`metrics/`、`trace/` 下其余集合用法逐一判读，说明为何它们不构成同类缺陷——避免后来者重新怀疑一遍。
5. **`verdict_drift` 能看见判分实现版本这根轴**（并入项）：口径聚合纳入 `grader_versions`，且**只纳入本次判定实际产出结论的评分器**（现字段取的是全部注册评分器，直接并入会让任何无关评分器改版都污染归因）。同时把"哪一根轴不同"变成输出字段——只修计数仍不够，`distinct_calibers = 2` 依然不告诉人是哪一轴，而本变更的验收记录正是卡在这一步。
6. **验收证据必须可在他机复现**：本变更引用的驱动脚本、以及 ⑤ 遗留未提交的活跑修复脚本，一并纳入版本控制。归档记录引用只存在于本机的代码，是连续两次出现的同一类缺陷。

**无公开面破坏**：`AgentRunner` / `Grader` 协议、`/v1` 响应结构、`eval-suite` 参数均不改动。`verdict_drift` 输出处新增字段为追加；`distinct_calibers` 名称与类型不变，其**值**变得更准——这是纠错而非契约变更。

## Capabilities

### New Capabilities

（无。）

### Modified Capabilities

- `graders`：新增「判分提示词必须对同一输入确定」这条要求。现有 9 条要求覆盖了结论自陈所见、按声明级别取信、披露最弱证据级别，但**没有任何一条约束判分输入本身的可复现性**——而这三条自陈类要求的可信度都建立在"重评看到的是同一份东西"之上。
- `orchestration`：新增「跨判定条目的翻判归因必须指明变化在哪一根口径轴」这条要求。既有条目只承诺"记录随结论落盘、可按 trial 查看"，未约束**跨条目聚合时能否归因**；本变更的实测正是从这条缝里掉出去的。既有 Requirement 与场景本文不动。

## Impact

- **代码**：`graders/model_based.py`（`_build_prompt` 一处 + 版本常量）；`core/runner.py`（`verdict_drift` 的口径聚合元组与新增的差异轴输出）。
- **测试**：`packages/agent-eval/tests/` 新增跨进程提示词一致性测试、评分器强度唯一性测试、翻判归因轴测试；现有 `model_based` 单测若断言过工具清单顺序需同步。
- **验收驱动脚本**：`_verify_judge_prompt_determinism.py`、`_verify_replay_archived_prompts.py` 从仓库根未跟踪状态入库（位置与命名按仓库惯例调整）。
- **遗留收口**：`examples/achat/run_live_acceptance.py` 的 ⑤ 活跑修复（`max_tokens` 300→1500 + 空 content 显式报错）仍未提交，随本变更一并入库。
- **数据**：历史 run 无需迁移。`statistics_version` 维持 2——本变更改的是判分输入的确定性与归因输出，不动分母口径；受影响的是评分器自身的 `implementation_version`。
- **版本**：随 0.4.0 发布（0.3.0 尚未发布到 PyPI，无跨版本兼容负担）。
- **依赖**：无新增运行时依赖。
- **验证门**：`cd packages/agent-eval && pytest tests/ -q` + `ruff check packages/agent-eval` 双范围。跨进程测试必须真起子进程——**不得用 `PYTHONHASHSEED=0` 自证**，那会掩盖缺陷而非验证它。
- **解锁**：判分器呈现不变性测量（bias probe 线）。那条线的全部意义就是把翻判归因到"呈现算子"这一根轴上——`grader_versions` 都进不去的元组装不下它。第 5 项修完，P1 少一个前置。
