## Context

`pyproject.toml` 写 0.3.0，`git tag` 停在 v0.2.0（2026-09-06），`CHANGELOG.md` 的 `[Unreleased]` 压着六个已归档变更且缺 ⑧ 一段。动机与证据见 `proposal.md`。

先例给了一条可直接复用的程序：`2026-09-06-make-published-artifact-match-accepted-code` 的第 4 步是"发布前**从构建出的 wheel/sdist 装进干净环境**跑一次离线示例与测试，通过后才打 tag"。那次之所以存在，正是因为工作树状态与发布物状态不是一回事。

约束：

- PyPI 不允许重传同一版本号。版本号一旦用错就永久错，所以它必须在构建物验证**之前**定死。
- 打 tag 与上传 PyPI 是对外可见且不可逆的动作，不属于可自动执行的本地操作。
- 六个变更的验收记录各自完整（④–⑧ 全部任务勾完，其中 P0 与 ⑧ 的活跑/替身证据已入库），本变更**不重开**它们的判定。

## Goals / Non-Goals

**Goals:**

- 让 `pip install aeval-framework` 得到的那份，等于仓库验收过的那份。
- 让 CHANGELOG 成为可引用的发布史：每个版本号都对应一个真实存在的发行物，每段都写在该段下。
- 把"已发布"的证据从"命令返回 0"换成"从索引回读成功"。

**Non-Goals:**

- 不动任何 `src/` 代码、主 spec 或测试。若发布前验证暴露出需要改代码的问题，那是**回归**，应另立变更而不是在发布流程里顺手修。
- 不发 dashboard。`apps/dashboard` 是 Next.js 应用，不随 PyPI 发行物走。
- 不补 `dataset` 的 spec、不测真实 judge 敏感度、不回填覆盖矩阵。见交接项。

## Decisions

### D1 版本号取 0.3.0

三个理由，第一个是硬的：

1. **`pyproject.toml` 已经写着 0.3.0。** 取 0.3.0 意味着这一步不需要改任何文件——版本号本来就是这么定的。
2. 版本号是**发布序列**不是**计划序列**。0.2.0 之后的下一个发行物只能是 0.3.0；跳到 0.5.0 会让 0.3.0 与 0.4.0 成为"从未存在过的版本号"，此后任何人拿 CHANGELOG 的段落去比对 PyPI 都对不上。
3. 0.x 期间破坏性变更走 minor 是既有做法：0.1.0→0.2.0 就带着 ③ 破坏的 `AgentRunner.run()` 签名。④ 破坏 `Metric.measure()` 走 0.3.0 完全一致。

*被否的备选*：

- **取 0.5.0**（迁就 ⑦ 声明的最高标签）—— 否决。那等于让六个计划各自的历史标签决定一个发行物的编号，且永久烧掉两个号。
- **取 0.4.0**（迁就 ⑤ 与 P0 的标签）—— 否决。跳过 0.3.0 会让 `pyproject.toml` 当前值成为一个从未发布的号，而这恰恰是本变更要消灭的状态。

**代价与缓解**：若干归档记录与 CHANGELOG 段落里写着"目标 0.4.0 / 0.5.0"。不静默改写它们（那是历史），而是在 CHANGELOG 收敛时加一行映射说明：这些标签写在"各版本单独发布"的假设下，该假设未成立，六个变更实际同批发布于 0.3.0。

### D2 从构建物验证，不从工作树验证

验证对象是 `python -m build` 出来的 wheel/sdist 在**干净环境**里装出来的那份，不是工作树。

*备选*：工作树跑绿就发。否决 —— 这正是先例那次事故的成因，且 898 条测试全绿证明的是源码，不是打包清单。src-layout 下最容易出的问题是数据文件（内置价目表、entry-point 组、`examples/` 引用资产）没进 `pyproject` 的打包配置，而这类问题**只有装出来才暴露**。

具体要覆盖的读法：`eval-suite extensions`（三个 entry-point 组是否发现得到）、`eval-suite run examples/minimal/suite.yaml`（离线端到端）、`/v1/meta` 起一次（API 分组与能力清单）、以及 `eval-suite power` 与 `--baseline`（⑥ 的两个新入口）。

### D3 发布后必须回读，退出码不算证据

上传成功不等于发布成功。回读三件事：索引里解析得到新版本号与元数据 → 干净环境按版本号精确安装一次 → 装上后跑离线示例并核对退出码与输出内容。

理由与仓库既有纪律同源：不能用管道后的退出码下结论，也不能用"命令没报错"下"已对外可用"的结论。中间任何一环都可能静默降级（镜像延迟、sdist 缺文件、平台 wheel 不匹配）。

### D4 ⑧ 的 CHANGELOG 段落必须带上那条结构限定

不只写"新增呈现探针"。必须写清 `dimension_order` 今天**测不出首因效应**：等权平均对维度排列对称，跟随位置的偏置不会移动合成分，故其 `not_detected` 比标签听起来弱。

理由：发布说明是外部读者唯一会读的东西。归档记录里的限定只有翻仓库的人会看到，而一个人照发布说明去引用"探针未检出排序敏感"就会引用错。**把限定写进发布说明的成本是一行，不写的代价是一个可被公开引用的误读。**

### D5 对外动作单独设闸

打 tag 与 PyPI 上传各自一步，标注为需现场确认，且排在所有本地验证之后、不可自动执行。回读验证若失败，**不回收 tag、不重传版本号**（做不到），而是立即发一个补丁版本并在 CHANGELOG 记因——所以回读必须在打 tag 之前以"预演"形式跑通一次。

### D6 README 的 Known Limitations 逐条判读，不按印象改

现有标题写着 "what **v0.1.0** does and does not do well"，其中若干条的事实已被 ⑤⑥P0⑧ 改变（探针、功效分析、多轮会话、套件打包）。判据：**逐条问"今天还成立吗、还准确吗"**，改的是失实的条目，不是全部重写。特别地，"regrade 是 library-only" 这类陈述在 ⑧ 之后需要复核——探针同样是 library-only，两者应同处一段说明，别让读者以为框架没有任何判分器内省手段。

## Risks / Trade-offs

- **[PyPI 上现有版本未知，别假设还是 0.1.0]** → 第一步就用网络核对索引拿到事实。先例那次记的是 0.1.0，此后 v0.2.0 是否真上传过、以及 0.3.0 是否被占用，都必须实测而非推断。
- **[干净环境验证可能暴露工作树验证不到的缺陷]** → 这是好事，也正是做它的理由。但要有预案：若暴露，本变更**停在打 tag 之前**，另立修复变更，而不是在发布流程里改代码（见 Non-Goals）。
- **[版本号标签重述会让历史记录看起来被改过]** → 不修改归档记录，只在 CHANGELOG 加一行映射说明。历史保持原样，收敛发生在发布说明层。
- **[六个变更里有 ④ 的破坏性签名变更，新使用者会撞到]** → 发布说明必须点名迁移路径（④ 已声明"不保留 legacy 旗标"），且 `docs/getting-started.md` 里那句"升级后哪些门会开始挡"需在 D6 一并核对。
- **[CHANGELOG 补 ⑧ 段属于事后补写，可能写偏]** → 以 ⑧ 的归档 proposal 与两条 spec 增量为唯一事实来源逐条对照，不凭本次会话的记忆写。

## Migration Plan

1. 网络核对 PyPI 现状 → 定死版本号（D1）。
2. 补 ⑧ 段 + 收敛 `[Unreleased]` + 加版本映射说明（D4）。
3. README Known Limitations 逐条判读（D6）。
4. 构建 → 干净环境装 → 覆盖 D2 列的四类读法。
5. **回读预演**（用测试仓库或本地索引，不对外）。
6. 现场确认 → 打 tag → 上传 → 对外回读（D3、D5）。
7. 回读失败时：不回收、不重传，发补丁版本并在 CHANGELOG 记因。

## Open Questions

- 是否需要一个 rc 预发布版本。0.x 阶段且无外部使用者依赖发布节奏时，直发更简单；若 D2 的干净环境验证发现问题较多，再引入 rc。属执行期可判。
- `docs/release-checklist.md` 目前写的是"把评测套件当公开数据集发布"的卫生清单，不是包发布程序。是否把本变更走通的包发布步骤沉淀进去——属工具改进，不阻塞发布。
