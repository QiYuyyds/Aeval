## ADDED Requirements

### Requirement: 未安装 CLI 依赖时命令行入口必须给出可行动指引

当发行包被以**不含命令行依赖**的形态安装时，命令行入口 MUST NOT 以一条指向内部依赖缺失的原始 traceback 结束；它 MUST 说明"命令需要哪一个安装形态"并给出可直接复制的安装表达式，且退出码与错误文本可被脚本判别。声明为可选依赖的入口点在缺少其依赖时**仍可被执行**这一事实本身不可消除，因此"说清缺什么"是 MUST，不是 SHOULD。

#### Scenario: 裸装后执行命令行

- **WHEN** 使用者按发行说明首行的最简形态安装，随后执行命令行入口
- **THEN** 得到的不是指向内部依赖模块的 traceback，而是一条指明"该命令需要带命令行依赖的安装形态"并给出可复制安装表达式的输出，退出码非零

#### Scenario: 已装齐依赖时零影响

- **WHEN** 使用者以带命令行依赖的形态安装
- **THEN** 引导路径完全不介入，其行为与本要求存在前逐字节一致（不得为了指引而改变正常路径的输出）

## MODIFIED Requirements

### Requirement: run demo 零 setup 首跑

`eval-suite run demo` SHALL 解析内置 starter pack 并完整运行（suite-distribution 的内置分发语义）；`demo` 不是文件路径，与同名本地文件冲突时本地路径优先并给出提示。本要求所称的"pip 安装形态"指**对照源码 checkout 的安装方式**，且 MUST 明确其假设的安装形态包含命令行自身所需的可选依赖 —— 只写"仅 pip 安装"而把依赖形态留成空白，会使该场景在真实世界里无人可执行。该场景 MUST 在**独立的干净环境**中以真实安装产物验证，MUST NOT 以仓库工作树内切换目录的方式替代（后者验的是源码树，不是发行物）。

#### Scenario: pip 安装形态下首跑

- **WHEN** 在一个不含仓库 checkout 的干净环境中，以包含命令行依赖的安装形态装上发行包，执行 `eval-suite run demo`
- **THEN** 内置套件完整运行并输出报告，全程离线，且其结果与仓库树内运行同一命令一致

#### Scenario: 以工作树内运行冒充发行物验证不算通过

- **WHEN** 有人报告该场景"已通过"，而验证方式是在仓库工作树里切目录后执行
- **THEN** 该报告不构成验收证据 —— 它证明的是源码可跑，不是发行物可跑；须改在干净环境以真实安装产物重跑
