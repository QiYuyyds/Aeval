## Context

只写影响做法的事实。动机见 `proposal.md` — Why。

- 两个并发会话在同一段时间里对这两个仓库都有提交动作（已发生：某会话把宿主 `TRACE_MAPPING_ENTRIES`、`run_first_suite.py` 判空并入 `3357a63` 提交；又有一会话把 Aeval 的 `trace/mapping.py` 提交而**把配套的 4 条测试留在了工作树**）。所以"提交了一半"是这个环境的常态风险，不是假设。
- 任务清单的可信度已经崩过一次：`add-openinference-mapping-preset/tasks.md` 勾了 19/25，其中 5 条"未办"有 4 条实际已完成（文档、`/v1/meta`、`--vocabulary` 都在）；③ 的 49 条勾选全部由别的会话写入，我没有一条亲自验证过。
- `openspec/specs/` 与归档移动都还是 untracked —— 主 spec 语料只存在于磁盘。
- 发布链路：`publish.yml` 由 tag push 触发，用 `pypa/gh-action-pypi-publish`，需要 `PYPI_TOKEN` secret。PyPI 不允许撤回已发布版本。
- 宿主的可运行性依赖 `pip install -e <本地 Aeval>`（`--no-deps`），因为 PyPI 上没有能配对 ③ 契约的版本。

## Goals / Non-Goals

**Goals:**

- 让"clone + 按 README 装"得到的是我们验收过的那份代码。
- 归档动作建立在**验证过的勾选**上，而不是别人写的框。
- 发布前有一次真正等价于外部用户视角的检查（从制品安装，而不是从工作树跑）。

**Non-Goals:**

- 不改任何软件行为，不新增 Requirement（`skip_specs: true`）。
- 不重写 CI/发布自动化，不引入 TestPyPI 流水线改造（若需试发布，见 Open Questions，另议）。
- 不在本变更里做 ④⑤⑥，也不做 D7 那个宿主假零修复（属宿主仓库自己的变更）。

## Decisions

### D1：版本号取 `0.2.0`，不取 `1.0.0` 也不取 `0.1.1`

③ 破坏了接入契约，但统计语义、指标目录、覆盖面都还在动。

- 不选 `0.1.1`：它把破坏性变更藏进补丁号，外部用户按语义化版本升级时不会预期签名断裂。
- 不选 `1.0.0`：①②③ 之后能力面仍小（10 个能力 44 条契约，成本轴还没价目表），1.0 会被读成"接口稳定"，而 ⑤ 还计划再动 trial 数据形状。

### D2：顺序固定为「落盘 → 核对 → 归档 → 版本与迁移说明 → 从制品验证 → tag」

每一步都是下一步的前提：

- tag 必须指向**已归档、已核对**的那棵树，否则发出去的版本对应的 git 状态里仍留着"进行中的 change"。
- 归档必须先于版本，因为归档会重写 `openspec/specs/` 与 change 目录位置；版本提交若在前，会把"未归档状态"固化进 tag。
- 从制品安装验证必须**先于** tag —— PyPI 不可撤回，这一步是唯一能证明"外部 clone 的人拿到的东西可用"的检查，而工作树跑绿不能证明打包完整（今天的经验：新模块曾处于 untracked 状态）。

### D3：核对以"实跑证据"为准，逐条产出结论

对两个 change 的每一条已勾选项：要么找到对应测试/命令输出，要么改回未勾并说明。特别是 ③ 的四类核心行为——来源三级、判定时刻、重评不覆盖、宿主迁移——必须各自有可指认的用例。

- 不选"抽查"：这一天里两次静态推断（属性名审计、安全规则是否触发）都被现场数据推翻，抽样不足以兜底。

### D4：README 的安装段在 0.2.0 落地前不写死版本号

否则文档会持续指向坏版本。写成"发布后 `pip install aeval-framework`，从源码 `pip install -e ./packages/agent-eval`"两种路径并列，并在迁移说明里点名 ③ 破坏的签名与 `trace_mapping=` 的接入方式。

### D5：宿主迁移与框架变更成对提交，但各自一笔

两个仓库各有自己的版本历史与并发提交者，跨仓库单提交不可能；但必须同一时段完成，否则窗口期里"两个 HEAD 不配对"的状态一直存在（即当前状态）。

## Risks / Trade-offs

- **PyPI 版本不可撤回** → 缓解：tag 与发布前必须逐次取得用户确认；发布后立刻从公网制品装一次并跑同一套离线用例作为复验。
- **勾选由别的会话写入，可能虚标** → 缓解：D3 的逐条实跑核对；发现虚标改回未勾并记在 tasks 里，而不是替它圆。
- **归档顺序写反**（`③ → preset` 也能过校验但会造成主 spec 里 `trace-provider` 的 Purpose/需求归属来回改写）→ 缓解：固定 preset → ③，并在归档后 `openspec validate --all --strict`。
- **从制品验证可能暴露工作树跑绿掩盖的打包缺漏**（新模块未纳入 wheel、模板/数据文件缺） → 这是**目的**而非事故：它必须发生在 tag 之前。`packages = ["src/agent_eval"]` 是目录式的，新模块应自动入包，但仍要实测。
- **并发提交者在我们提交期间动同一批文件** → 缓解：每笔提交前重新读 `git status`，只点具体路径，不用 `git add -A`（今天已两次证明这个环境里会出现别人的改动）。
- **0.2.0 是破坏性版本但没有迁移文档** → 缓解：迁移说明作为版本提交的一部分，不接受"先发后补"。
