## ADDED Requirements

### Requirement: 用户侧由模拟器协议供给而非写死单轮

框架 MUST 提供一个用户侧扩展协议，使一个 trial 的后续输入可以在运行中被决定：该协议 MUST 至少支持两种实现模式 —— 预写话术（按序给出，不调用任何模型）与目标驱动（依据任务目标与已有轨迹生成下一句）。模拟器产出的每一条用户消息 MUST 作为带来源标记的观测进入证据，且其来源级别 MUST 为评测侧（与运行中探针同级），MUST NOT 记为被评方自报。既有「交给被评系统的任务信息不含答案键」的信息屏障 MUST 同样适用于模拟器：模拟器 MUST NOT 获得期望输出或任何答案键，否则答案会经由对话被洗进被评系统。目标驱动模式缺少可用的语言模型配置时，MUST 返回带原因的不可用结论，MUST NOT 让 trial 崩溃或被折成失败。模拟器输入视图 MUST 能回答「我在为哪个 task 工作」（任务标识与描述），使按域或按人设切换实现的模拟器无需靠猜测或靠外部上下文；视图里存在的字段 MUST NOT 在正常执行路径上恒为空。会话的轮数上限 MUST 在向模拟器索取下一条话术**之前**判定；已达上限时 MUST NOT 先生成一条再丢弃 —— 真流量下被丢弃的那一次就是一次白付的模型调用。

#### Scenario: 模拟器拿不到答案键

- **WHEN** 一个目标驱动模拟器在一个带期望输出的 task 上生成第 2 轮话术
- **THEN** 它能看到的只有任务描述、目标与本 trial 已有的用户与 agent 消息
- **AND** 期望输出与答案键不在其输入内，无法经由对话泄露给被评系统

#### Scenario: 预写话术跑完整会话

- **WHEN** 一个多轮任务声明了三句预写用户话术并被执行
- **THEN** 被评系统依次收到这三句加上首轮输入，轨迹里每条用户消息都标注为评测侧来源与其时刻
- **AND** 整个过程没有产生任何模型调用

#### Scenario: 目标驱动模拟器缺配置

- **WHEN** 任务声明使用目标驱动模拟器，而运行方未注入语言模型回调
- **THEN** 该判据给出带原因的不可用结论，指明缺的是哪一项配置
- **AND** 同一 run 的其他 trial 照常完成

#### Scenario: 模拟用户读数不得被当成被评方证据

- **WHEN** 一个只取信评测侧证据的判据遇到一次含模拟用户消息的会话
- **THEN** 模拟用户消息对它可见（属评测侧来源），而被评方的自报状态仍按既有规则排除

#### Scenario: 模拟器知道自己在为哪个任务工作

- **WHEN** 一个按任务域切换人设的模拟器（如零售域与电信域）在某 task 上被调用
- **THEN** 它的输入视图里带着该 task 的标识与描述，据此选出正确的人设
- **AND** 测试断言这两个字段非空 —— 声明了却恒为空的字段比没有该字段更危险，它会让实现以为拿到了

#### Scenario: 轮数上限在生成之前生效

- **WHEN** 一个目标驱动会话的上限是 3 轮，已消费 3 轮后适配器再次索取下一条用户消息
- **THEN** 会话以「轮数上限」原因结束，且**没有**为这条注定被丢弃的话术发起模型调用
- **AND** 诊断块记录的轮数与模拟器调用次数一致，可事后核对没有白付的调用

### Requirement: 运行中事件钩子挂载在框架产出的会话对象上

框架 MUST 在其构造的会话对象上提供运行中钩子：注入环境事件、注入一条人工介入消息。事件与介入消息 MUST 带采集时刻进入轨迹证据，并 MUST 在报告与结论中可与普通消息区分。宿主实现的被评系统协议、评分器协议与环境协议 MUST NOT 因本能力而改变签名 —— 新钩子只增加框架产出对象的能力。既有适配器若不消费这些钩子，单轮任务的行为 MUST 与本变更前逐位一致。

#### Scenario: 运行中注入环境事件

- **WHEN** 一次会话在第 2 轮之后被注入一个环境事件（如文件被外部改动）
- **THEN** 该事件出现在轨迹证据中并带时刻，且能被声明取信轨迹通道的判据读到
- **AND** 结论可以指出该事件之后的状态变化

#### Scenario: 人工介入参与判定

- **WHEN** 一次 trial 中途被注入一条人工消息
- **THEN** 该消息作为评测侧观测落盘，且 trial 结论标注它含人工介入

#### Scenario: 旧适配器不受影响

- **WHEN** 一个变更前写好、只走单轮的适配器运行一份不含 `conversation` 的套件
- **THEN** 其行为与本变更前一致，不出现任何新的缺失告警

### Requirement: 扩展点经发现机制注册且不保留双路径

框架 MUST 能从安装元数据中发现第三方的评分器、环境管理与用户侧模拟器实现，并将其注册进运行时的同一份注册表；该注册表 MUST 是 CLI 与 API 装配运行时使用的唯一来源，MUST NOT 存在「一处注册给命令行、另一处注册给接口」的并行装配路径。名字冲突时 MUST 显式报错并指出冲突的两个来源，MUST NOT 静默覆盖。发现失败（元数据损坏、导入异常）MUST 记为可诊断的告警而不是让运行整体启动失败。

#### Scenario: 安装包自带的自定义评分器被命令行直接使用

- **WHEN** 一个已安装的包通过 entry point 声明了一个自定义评分器，用户从命令行运行引用它的套件
- **THEN** 该评分器被解析并执行，trial 结论携带其证据声明
- **AND** 用户不需要编写任何构造运行时的代码

#### Scenario: 同名冲突不静默

- **WHEN** 两个已安装的包注册了同名的评分器
- **THEN** 装配期报错并列出两个来源，运行不开始

#### Scenario: 损坏的元数据只告警

- **WHEN** 某个包的 entry point 指向一个导入失败的模块
- **THEN** 框架记录该扩展点不可用的告警并继续装配其余扩展点
- **AND** 若套件恰好引用了它，则按未注册处理给出 `unknown_grader` 结论
